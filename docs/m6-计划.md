## 2. 诊断结论(四个透镜去重后)

### 2.1 FT 在开发集的 51 道失败,按机理分解

- 计数(`runs/eval/select-ft/checkpoint-1668.score.json`,`summary.error_classes`):值或格式错 23、选错工具 13、该追问没追问 11、不该调却调 2、多参 1、恢复不当 1;JSON 损坏、思考块泄漏、编号编造、缺参、重试风暴均为 0(`json_valid_rate` 1.0、`ids_grounded_rate` 1.0)。格式不是误差来源:本地提示就是训练样本的渲染(`src/research_agent/train/samples.py` 的 `prompt_renderer`,`docs/m2-进度.md` 已核验逐字节相同)。
- 按机理(误差透镜 `analyze_hypotheses2.py` 第 [G] 节,与 B2 配对):
  - **决策类 26 道**(该查哪个工具 / 先查还是先问 / 继续还是收尾)。其中 list_notes 与 search_notes 混淆 4 道(请求同时带 since 与 tag);该追问没追问 11 道的共同形态是「再查一轮而不是问」(9 道查笔记、2 道查 arXiv)。
  - **默认值惯例 13 道**:唯一不同的参数是带默认值的可选参数——`search_notes.top_k=5`(默认 3,`src/research_agent/tools/schemas.py:101`)7 道、`list_notes.limit=20`(默认 10,`:114`)3 道、`search_arxiv.sort_by=submittedDate` 2 道、`max_results` 1 道。机理:模型看到的工具表删掉了 `default`(`schemas.py` 的 `_VALIDATION_ONLY`),判分前双方按默认值填充(`metrics.py:209-214`),所以「不写」等于「写默认值」,写成非默认常量就是错。
  - **中文主题词英译失败 6 道**(全部 zh;「测试时扩展」5 道、「混合专家」1 道);英文题 26/27 正确。
  - **追问的 missing 多报 4 道**(hw-dev-041 多报 mode、hw-dev-043 多报 date_range、req-dev-0133-s3 与 0152-s4 多报 topic)。
  - **用户明说放宽条件后仍保留日期 2 道**(hw-dev-049、053;053 还编出 `date_to=2026-10-31` 晚于「今天」,触发硬路由)。
- 与 B2 配对(`runs/eval/dev-b2-m3.jsonl`,90.0%):两者都对 96、只有 B2 对 39、只有 FT 对 3、都错 12。B2 对而 FT 错的 39 道:决策 21、惯例 10、知识 5、missing 多报 2、指令 1。都错的 12 道全是手写题,其中 8 道 B2 也败在同样的老师惯例上(hw-dev-060 写 top_k=5、hw-dev-056 写 limit=20、hw-dev-041/043/045 missing 多报)。**手写金标准的「最小参数、最小 missing」约定与老师习惯系统性冲突,FT 继承了这个天花板**;测试集手写占比 43.3%(130/300)高于开发集的 31.3%(`data/eval/sets-manifest.json`)。
- 离线复核(只改 FT 输出、不改判分器,本草案重跑 `analyze_hypotheses2.py` 第 [F] 节确认):删去 FT 输出里的 `search_notes.top_k==5` 与 `list_notes.limit==20` 后,开发集 109/150(72.7%,+10 道、0 道变坏);`min_decision_prob` 的 AUROC 从 0.674 升到 0.740;冻结阈值下同样转交 94 道时 FT+R 从 132 升到 137(91.3%)。再删 `sort_by` 则 +12 −3,再删 `max_chars==1500` 无变化。这是开发集上拟合的上界,不是预测。

### 2.3 路由信号(`runs/m4/dev-ft-signals.jsonl`,路由透镜 `report.json`、`policies.json`)

- `min_decision_prob` 的 AUROC 0.674 几乎全部来自中文题与调用型题:按题型 call 0.725、recover 0.719、no_call 0.708、parallel 0.708,但 next_step 0.340、clarify 0.440(反向);按语言 zh 0.756、en 0.547。原因:长文本回答(最终回答、追问句)的首 token 概率天然偏低。
- 冻结点(阈值 0.689,94 道转交,88.0%,0.323 元/百道)的成本虚高来自误转交:94 道里 53 道 FT 本来就对;纯文本回答 32 道 FT 全对、无一道属理想转交集合,却有 18 道被转交,占成本 0.080 元/百道(25%)。
- 高置信却答错的 10 道(mdp 0.712–0.861,未转交)里 8 道是「值或格式错」,7 道正是惯例差(top_k=5 / limit=20 / sort_by)——概率信号原理上抓不到学来的习惯,一条读参数值的规则完全可见:标志 habit(`top_k≠3` 或 `limit≠10`)命中 27 道,其中 21 道属理想转交集合(39 道),FT 对的只有 1 道。
- 硬触发在开发集零边际价值:只触发 2 道,且两道的 mdp 都已低于阈值;测试集 8/300。
- 离线策略模拟免费(B2 的 150 道开发集回答全部已缓存):P1 文本回答豁免 → 88.0% @ 0.242 元/百道(成功率不变、成本 −25%);P5 = P1 + habit 硬触发 → 阈值不动即 91.3% @ 0.258(137/150,高于 B2 的 90.0% @ 0.463);P5 重扫阈值(样本内)88% @ 0.181(转交 52 道)、90% @ 0.230。理想路由按成本:88% 只需 0.086 元/百道、92.0% 需 0.133(`results/cost-oracle-m4.json`);任何路由的上限是 138/150 = 92.0%(12 道双错 + 3 道 FT 对 B2 错)。
- 嵌套留一法逻辑回归(5 个可观测特征:log mdp、is_text、habit、n_args、notes_tool)AUROC 0.906,只用结构特征不用对数概率 0.897,mdp 单独 0.645:概率信号在结构特征之上几乎无增量;但特征是看过开发集逐题结果后设计的,嵌套 CV 只校正 λ 的选择,不校正特征设计。
- 逐 token 信号(熵、裕度)无法离线算:`src/research_agent/eval/runner.py:107-108` 只落盘三个汇总值,`runs/` 下没有 `top_logprobs`;采样一致性从未采样。
- 端到端:冻结阈值 + 「一旦转交就留在云端」让开发集 20 个任务里 19 个途中整体交给 B2(本地 11 步 / 云端 64 步,`docs/m4-进度.md`),测试集 60 个里 58 个(本地 30 / 云端 194),端到端成本接近 B2。
- 测试集上的教训(`results/test-m5-ftr.json`):FT+R 78.7% 只比同比例随机路由 77.7% 高 1.0 pp(开发集高 7.0 pp);冻结点在开发集恰好踩线,没有延续到测试集。

### 2.4 配方与学习曲线(`runs/train/ft/log.jsonl`、`results/checkpoint-selection-ft.json`)

- 8 个检查点的开发集成功率 51.3/55.3/55.3/60.7/58.7/62.7/62.7/66.0% 单调上升到最后一步,但末段 +5 道发生在学习率 < 4.1e-6 的退火段,第 2 个 epoch 的训练损失已走平(各 1/8 窗口均值 0.496/0.491/0.507/0.491),同位置损失比第 1 个 epoch 低 0.127。
- 分题型不同步:no_call 第 209 步即 92%、recover 第 836 步即 80%;clarify 8 个检查点从未超过 30%;值或格式错保持 17–23 道不降。**同款数据再训不会修好 clarify 与值或格式错。**
- B4(只用公开数据)第 417 步后下降(38.7% → 28.7%),`false_call_rate` 升到 0.84–0.96:公开数据越训越逢题必调;它在混合训练里只能起防遗忘作用,而 ACEBench 上它没有起到(B4 36.18% ≈ FT 35.72%)。

- 老师在开发集 clarify 上也只有 75.0%(`docs/m3-进度.md`),是蒸馏的上限。

### 2.5 ACEBench 退化的机理(`results/acebench-m4.json`、`runs/acebench/m4/`)

- 不是换回 `<tool_call>`:normal 组 1,640 条回答里 0 条含它。
- normal 组的降幅全部来自表层语法:可解析回答 FT 530/817(zh)、575/823(en)对 B0 687、700;以可解析为条件的正确率 FT 0.560 / 0.605 对 B0 0.574 / 0.570,工具选择与填值没有退化。三种破坏形状(FT 对 B0):嵌套对象写成 Python kwargs `{key=value}`(zh 98 对 56、en 154 对 49)、调用写成 JSON 列表 `[{"name":…,"parameters":…}]`(zh 83 对 0、en 17 对 0)、复制指令占位符 `ApiName(` 并循环到 token 上限(含该字面的回答 zh 48、en 53 对 B0 23、0)。kwargs 破坏集中在带字典型参数的类别(single_function 95/100、parallel 98/100、object 50/50 的标准答案含字典值参数)。
- special 组(zh 19.33% → 3.33%,en 27.33% → 3.33%)是「不用规定句式 + 照样发起调用」:B0 用了规定英文句式的回答 125/150(zh)、129/150(en),FT 24、33;FT 在 incomplete/error_param 上照样发起调用 zh 61/100、en 30/100,B0 两种语言都是 0。
- 根因与训练分布一致:5 个公开数据文件 4,000 条记录全部没有 system 消息(`src/research_agent/data/public.py` 的转换器丢弃来源的系统提示与格式指令),1,187 条合成记录共用同一个中文系统提示;格式指令只以聊天模板的 `<tools>…<tool_call>` 一种形式出现;13,331 个样本的补全都是这一种格式。ACEBench 把函数与格式写在系统提示文本里、不传 tools 字段。
- 合成数据与步数都不是主因:B4(只用公开数据、第 417 步)退化幅度相同;FT 的开发集成功率随步数单调上升,少训几步只损失目标 (1)。
- BFCL(用 Qwen 模板传工具)上 FT 78.03% 不低于 B0 75.90%,只有 live_irrelevance −10.86 pp(`results/bfcl-m3.json`)。
- 本机 HF 缓存里未用过的公开记录:toolace 10,586(已用 1,500)、glaive_v2 112,745(已用 800;其中不调用对话 49,574)、hermes 6,871(已用 700)、deepexi 23,961(已用 500)、glaive_zh 997(已用 500)(`data/public/manifest.json`);新文件进训练前须重跑 `scripts/check_benchmark_overlap.py`,训练脚本对未登记文件拒绝运行。

## 5. 预登记草案(定稿后成为 `docs/m6-预登记.md`)

**目的**:检验在开发集上选定的两个新系统 FT2、FT2+R2;这是测试集的第 3 次也是最后一次打开。打开之后,任何新的结论都需要新的测试数据。

**被比较的系统**

| 系统 | 内容 | 运行方式 |
|---|---|---|

**假设与检验族**(Holm,$\alpha = 0.05$,3 个 $p$ 值)

| 编号 | 假设 | 终点 | 效应量与检验 |
|---|---|---|---|
| H1 | FT2 高于 FT | 单步成功率,全部 300 道 | $\hat\Delta_1 = \hat p_{\mathrm{FT2}} - \hat p_{\mathrm{FT}}$;配对 bootstrap 95% 区间(10,000 次,种子 42)与聚类 bootstrap(163 簇);配对精确 McNemar 的双侧 $p$ |
| H2 | FT2+R2 对 B2 非劣(余量 $\delta = 0.02$) | 单步成功率,全部 300 道 | $H_0: \Delta_2 \le -\delta$。$p_{\mathrm{NI}} = \#\{b : \hat\Delta_2^{*(b)} \le -\delta\} / B$,$B = 10{,}000$,逐题配对有放回重抽,种子 42;等价于单侧 $(1-\alpha)$ 百分位下界高于 $-\delta$。另报聚类版本(描述) |
| H3 | FT2 对 B0 在 ACEBench 上非劣(余量 0.02) | ACEBench 汇总 $\bar a$(30 个(语言, 类别)层准确率的算术平均,每系统 1,940 道) | $\hat\Delta_3 = \bar a_{\mathrm{FT2}} - \bar a_{\mathrm{B0}}$;分层配对 bootstrap:每层内逐题有放回重抽,层均值之差再取 30 层平均为 $\hat\Delta_3^{*}$,$p_{\mathrm{NI}}$ 同上定义,10,000 次、种子 42 |

- 三个 $p$ 值一起做 Holm 校正。H1 用 McNemar 的 $p$,H2、H3 用 $p_{\mathrm{NI}}$。区间不做多重校正。
- 终点不改为手写题子集:FT 与 B2 在测试集逐题的结果已在 M3、M5 看到,此时改口径等于看了数据再定;草拟题的金标准是 B2 的回答(170/300),H2 因此偏向 B2,照实披露,手写题子集只作描述。

**成功判据(事先写死)**

- 目标 (1) 达成:H1 校正后 $p < 0.05$ 且 $\hat\Delta_1 > 0$。
- 目标 (2) 达成:H2 校正后 $p < 0.05$,且 $c_{\mathrm{FT2+R2}} \le 0.169$ 元/百道(列表价,只计转交的题;FT+R 的 M5 值 0.338 的一半)。只满足后者记「成本达成、质量未达成」;只满足前者记「质量达成、成本未达成」。
- 目标 (3) 达成:H3 校正后 $p < 0.05$。

**描述性结果(不做检验)**:FT2+R2 对 FT+R 的差与区间、转交数与比例、硬触发与参数触发各计数、同转交比例与同成本的随机路由;按类别、语言、草拟与手写子集;11 类误差计数;FT2 与 FT2+R2 的一致性(本地作答的题与 FT2 的单步记录;转交的题与 M3 中 B2 记录逐字节相同的题数);时延 p50/p95(本地、转交、转交且付费)与显存;成本(实付、列表价折算、账本);端到端 60 任务的成功率、每任务本地/云端步数、有转交的任务数、花费(逐步路由下的新定义,与 M5 不可直接比较);ACEBench normal / special 分组、格式计数(可解析、`<tool_call>`、kwargs、JSON 列表、失控)、FT2 对 FT 的各层差;BFCL 11 类与汇总 FT2 对 B0、FT;探针分数与 ACEBench 的对照(探针的预测力)。

**开发集上的决定(打开前已完成、写进配置)**:选点规则与结果;路由规则、策略集合、目标函数、冻结点(转交数、成功数、成本);dev-ext 验证块;探针校准与 FT2 的探针分数;GO 门槛的核对。

- **开发集上定不了的**:测试集草拟金标准里老师显式写 top_k=5 / limit=20 / sort_by 的频率(A1 的测试侧净效应);测试集手写恢复题里 EMPTY_RESULTS 的占比(A4);中文术语样本对测试主题(蒸馏 / 循环深度 Transformer / 分词)的迁移(A5);路由规则特征的选择性偏差大小(嵌套 CV 不校正特征设计;dev-ext 是唯一留出);种子方差(只有 seed 42);探针对 ACEBench 的预测力(校准只有 3 个点)。
- **分辨率**:150 道上 1 道 = 0.67 pp、标准误约 3.9 pp;dev-ext 132 道组成偏斜(无并行题、草拟 90%);各候选的预期增益多在 +2 至 +10 道,叠加后能判,单项不能判——本轮不做单项归因,只用离线上界(A1)与探针(D1/D2)做部分归因。
- **污染类**:ACEBench 的失败模式分析进入了数据设计(披露;格式集合排除其记法;13-gram 门);开发集逐题结果进入了规则设计(披露;dev-ext 验证);最后一次打开之后项目没有未见过的测试数据,README 须写明;若在 M6 前公开仓库,测试题目对外可见(`docs/m5-进度.md` 已注明程序上仍有效)。
- **草拟题与手写题**:B2 是草拟题的金标准,H2 在全部 300 道上偏向 B2——FT2+R2 要在草拟题上接近 100% 只能靠转交或复现 B2 的回答;M5 的差距(−6.7 pp)正来自草拟题(87.6% 对 100.0%),手写题上两者接近(66.9% 对 66.2%)。H2 是本轮最可能不成立的假设;成本判据不受这一偏差影响。手写题子集只作描述,不改终点。
- **A1 的反向风险**:用户明确要 5 条笔记时 top_k=5 是对的——训练侧按 `slots.count` 保留,路由侧 C2 会把这类正确调用误转(开发集金标准 1/8 带 top_k=5),代价是多付一次 B2,不是判错。
- **A2 的误追问**:追问样本占比翻倍可能让完整请求也被追问;开发集 call 题目前 0 道误追问,FT2 上监控「不该追问却追问」计数,超过 2 道则在预登记里写明并考虑把 R3 的 300 条减半重训(+13.5 h)。
- **D1/D2 的稀释**:格式混合约占样本 11–13%,开发集估计 0 至 −2 pp;选点规则与 GO 门槛兜底;若 NO-GO 于开发集而探针通过,下一步是减半格式混合重训,不是放弃格式保持。
- **FT2+R2 的端到端新定义**(逐步路由)与 M4/M5 的「留在云端」不可直接比较;只作描述。
- **GPU 热饱和**:估计按 530–623 token/s。
- **本轮不做、记入残余**:续训、秩与模块消融、KL 正则、损失重加权、采样一致性信号、老师生成的定向轨迹、提示内术语表(A5')。
