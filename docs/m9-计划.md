# M9 计划:实时使用与文档收尾

**状态:所有者 2026-11-10 批准。**过程记在 docs/m9-进度.md。本计划不打开任何测试集,不使用留出集,不训练,云端 API 花费为 0。

## Context

- **起因。**M8 按预登记以 NO-GO 收尾后,最终系统仍是 M7 的 final(Nanbeige4.1-3B 的 QLoRA 适配器 FT3 第 1635 步、思考模式、推理预算 1,280、5 样本投票、2 条运行时规则,冻结记录 `results/final-m7.json`)。核查发现,它的全部评测都在 2026-10-10 录制的 300 篇论文语料上回放,还不能用于 docs/plan.md 写定的用途,即每周的 arXiv 阅读:
  - `Fetcher` 的 live 模式没有调用方;检索由本地语料索引代答;
  - 没有使用入口与使用说明;
  - 评测每个任务前清空笔记库,没有长期笔记;
  - 追问之后不能接着原请求继续。
- 另有文档缺口:M7 预登记承诺的几项描述没有做完(思考长度、超出训练长度的步数、final 在 20 个开发端到端任务上的运行、投票与规则计数),README 没有「决策」一节,`docs/m7-进度.md` 没有收尾一节。
- **所有者的决定:**补成能实际使用的助手,同时补齐文档。
- **目标:**
  1. `scripts/ask.py` 在真实 arXiv 上运行未经改动的 final,笔记长期保存,追问后可以接着回答,每步显示进度;
  2. 一次判据事先写定的实时冒烟测试,给出「可用 / 不可用」的结论;
  3. 补齐 M7 承诺的描述项与 README 的缺口;
  4. 刷新公开仓库。

## 不改动的部分

运行的必须就是被评测的系统。下列内容保持字节不变:

- `tools/schemas.py`(工具定义、`SCHEMA_HASH`、各项上限、上下文 4,096)与 `agent/prompts.py`(`PROMPT_VERSION`、`PROMPT_HASH`);
- `agent/loop.py`、`agent/context.py`、`agent/vote.py`、`agent/rules.py`、`agent/models.py`、`agent/executor.py`;
- `llm/generation.py`、`llm/local.py`、`family/`、`eval/systems.py`、`policy.py`、`validation.py`、`tools/adapters.py`;
- `notes.py` 的 `render_note` 与 `pick_evidence`;
- 底座 GGUF、适配器 GGUF 与分词器目录(SHA-256 见 `results/final-m7.json`)。

只允许三类改动:新增模块;只观察、不改请求的包装;新增关键字参数且默认值保持原行为。`live/frozen.py` 在每次启动时核对四个代码哈希(提示版本与哈希、工具定义哈希、规则版本)与冻结记录的全部取值,任何一项不符就拒绝运行。

## 工作包

### WP1 运行入口:`scripts/ask.py` 与 `src/research_agent/live/`

- **组装与核对(`live/frozen.py`)。**`load_frozen()` 依次核对代码哈希、`family.record()`、由 `GenerationSettings.for_family(family, mode="think", reasoning_budget=1280, base_seed=0)` 加 5 票得到的 `settings.record()`、规则与投票方式、两个 GGUF 的 SHA-256,以及 `results/test-config-m7.json` 的服务器设置(端口 8080、上下文 8,192、超时 120 s、llama.cpp b11349)。模型由 `eval/systems.py` 的 `build_system("ft", …, rules=True, vote_mode="final")` 组装;`identity_problems()` 核对服务器:恰好一个适配器、`total_slots` 为 1、构建号一致。
- **服务器。**默认自行启动 `LocalServer`(`--llama-server` 指定可执行文件,`-np 1`,`-c 8192`),启动前要求显卡空闲(占用不超过 1,500 MiB);`--server URL` 复用已在运行的服务器,同样经过 `identity_problems()`。
- **实时工具(`live/world.py`)。**
  - `Fetcher("live")` 配真实的 `build_search_url`、`parse_atom`、`extract_section`;
  - 限速记录各主机最后一次请求的时间(`runs/live/` 下),使 API 每 3 s 一次、HTML 每 15 s 一次的间隔在多次运行之间也成立;
  - 本轮搜索与 `get_paper` 得到的论文在进程内缓存,`write_note` 复用,不再重复请求;
  - `write_note` 外加一层:只在正文里见过的论文先查一次元数据;网络失败给 `RATE_LIMITED` 或 `UPSTREAM_ERROR`,不误报为 `NOT_FOUND`;
  - 笔记库默认在仓库的 `notes/`(不进 git)。
- **一轮的运行(`live/session.py`)。**
  - `today` 取本机日期,每轮取一次,同一个值传给系统提示、`ToolExecutor`、arXiv 工具与笔记工具;
  - 调用与评测相同:`run_turn(…, decide=policy.decide)`,没有转交模型;不调用会清空笔记目录的评测函数 `run_request` 与 `run_tasks`。
- **追问后继续。**`pack_follow_up(请求, 回答)` 原样保留请求、在末尾接上回答:中文请求为「请求补充:回答」,英文请求为「request To clarify: answer」,作为一条新的单条用户消息。训练与评测见过的都是单条、无换行的用户消息,中文模板用半角标点,这种写法离训练分布最近。最多补充两次,此后请使用者重新表述完整请求。
- **进度与输出。**
  - 包装层只打印、不改请求字节(测试比对请求字节):每步的投票一致数、思考长度、触发的规则、调用的工具与耗时,只用 ASCII 字符;
  - 每次运行写入 `runs/live/<时间戳>/`:`session.json`(身份核对结果)、`server.log`、`requests.jsonl`、每轮的 `turn-NNN.json`(完整转录)与 `turn-NNN.md`(答案、写入的笔记、引用的论文编号),并在 `runs/live/index.jsonl` 追加一行。
- **单实例锁。**操作系统级文件锁(Windows 用 `msvcrt`,其他系统用 `fcntl`),同一时间只运行一个 ask,进程退出时自动释放。
- **退出码。**0 正常;1 一轮中出现异常;2 组装或核对失败;3 锁被占用。Ctrl+C 时关闭服务器、释放锁后退出。
- **命令行。**
  - 单次:`ask.py "请求"`,可加 `--clarify-answer`;
  - 交互:`--interactive`(提示符 `ask>`,追问时 `answer>`;`/new` 开始新请求,`/quit` 退出);
  - 批量:`--batch FILE.jsonl`;
  - 只核对:`--check`;arXiv 探针(不用显卡):`--probe ID…`;
  - 导入已有笔记(可选,由所有者运行):`--import-notes FILE`,`load_entries` 新增 `skip_existing`,重复导入不产生重复条目,只打印计数;
  - 没有 `--today` 参数;测试以注入方式给定日期。

### WP3 实时冒烟测试

本节与请求文件 `configs/live-smoke-m9.jsonl` 在任何实时运行之前提交,运行后不改。这不是一次测试集打开,结果只作描述。

- **探针(不用显卡):**`ask.py --probe 2510.99999 cs/0112017`,外加一次实时检索;记录 HTTP 状态、默认解析与宽松解析各自的结果。
- **第 1 批(一个进程):**S01–S06,分别是中文找近期论文、英文按类别与时间窗找论文、中文查论文元数据、英文读引言、中文比较两篇论文、中文写一条 scaffold 笔记(请求原文见请求文件)。
- **第 2 批(另一个进程,检验笔记库重开与跨进程限速):**S07 英文检索笔记、S08 中文列出最近的笔记、S09 中文缺主题的请求(应当追问,用请求文件里的回答继续)、S10 英文查询不存在的编号 2510.99999(不得编造标题)。
- 冒烟笔记写入 `runs/m9/smoke-notes`,不混入日常的 `notes/`。
- **第一层判据(全部满足才判「可用」):**
  1. 两批的身份核对都通过;
  2. 11 轮(含追问后的一轮)都以 `run_turn` 的状态结束,没有异常,也没有由实时代码引起的 harness 错误;
  3. 请求日志中 API 请求间隔不小于 3.0 s、arxiv.org HTML 请求间隔不小于 15.0 s,任何时刻至多一个请求在途;
  4. S06 恰好写出一条笔记,证据句都能在该论文摘要中找到;第 2 批重新打开的笔记库能列出这条笔记;
  5. S09 第一轮以追问结束,追问后一轮的唯一用户消息等于 `pack_follow_up(请求, 回答)`;
  6. 未知编号给 `NOT_FOUND`,旧式编号在宽松解析下给空列表,实时检索有命中;
  7. 每轮的 `.json`、`.md` 与索引行都在,运行结束后工作区干净。
- **第二层(只报告,不判通过):**是否调用了预期的工具、引用的论文编号是否都出现在本轮工具输出中、步数、用时、思考长度、全票一致的比例、触发的规则。
- **第一层不通过时:**只修实时代码并补回归测试,11 轮全部重跑,两次结果都报告。
- **合规:**arXiv API 每 3 s 一次,HTML 按 robots.txt 每 15 s 一次;单连接、单进程(由锁保证);转录、笔记与探针结果只留在不进 git 的 `runs/` 与 `notes/` 中,报告只写编号、标题与计数,不引正文。
- **报告:**逐条结果与结论记在 docs/m9-进度.md;README 只写一句(请求数与结论)。

## 风险

| 风险 | 对策 |
|---|---|
| 实时 API 的特殊情况(旧式编号、未知编号、429、服务中断) | 宽松解析、错误码映射、事先探针 |
| 实时数据不同于冻结语料(排序、新主题、HTML 差异) | 冒烟只作描述;README 局限写明 |
| 一轮需要数分钟 | 显示进度;交互模式只启动一次服务器 |
| 显存冲突 | 显卡空闲检查、端口占用检测、单实例锁、两段显卡使用错开 |
| 导出规则失配 | README 只插入不改;先做试运行导出 |
